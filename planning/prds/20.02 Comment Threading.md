# PRD: Comment Threading

**Tier:** 2 &nbsp;·&nbsp; **Status:** Proposed &nbsp;·&nbsp; **Owner:** TBD

## Problem
Comments today are a flat list under each article (`apps/comments/models.py` has no parent reference). Readers can't reply to a specific comment — they can only post another flat comment that loses context. On articles with 20+ comments, the discussion devolves into "@janedoe re your point above…" which is exactly the workaround threaded comments solve. RealWorld-class blogging apps (Medium, Substack) all support at least one level of reply.

## Goals
- A user can reply to a specific comment; the reply renders nested under its parent.
- Threads cap at 3 levels of depth — replies to a depth-3 comment attach to the depth-3 parent, not depth-4.
- Reply form swaps in inline via HTMX, no page reload, no scroll jump.

## Non-Goals
- Comment voting, sorting by score, or "best" ordering — chronological is enough.
- Collapsing/expanding subtrees. All threads render fully.
- Editing comments. Out of scope; covered by a separate edit PRD if ever.
- Backfilling a parent on existing comments — they all stay flat (NULL parent).

## User Stories
- As a reader, I click "Reply" under a comment and an inline form appears below it.
- As a reader, I post a reply and it appears nested under the parent without losing my scroll position.
- As a reader, I see replies indented up to 3 levels; deeper replies indent no further.
- As an article author, I can delete any comment in any thread (current behavior preserved per `apps/comments/CLAUDE.md`).
- As a commenter, deleting a parent comment shows a tombstone ("comment deleted") so the children's context survives.

## UX Sketch
On the article detail page, each comment card grows a "Reply" button. Clicking it does `hx-get="/article/<slug>/comment/<id>/reply-form"` and swaps in a small textarea + Post button below the comment, targeted at a sibling div. Submitting the form does `hx-post` to the existing comment-create endpoint (now accepting `parent_id`), and the response is a re-rendered `partials/comment_list.html` (already used in delete view). Indentation is CSS — `--depth: 1|2|3` set on the wrapper, capped server-side.

## Data Model Changes
- Add `Comment.parent = ForeignKey("self", null=True, blank=True, on_delete=models.SET_NULL, related_name="replies")`.
- Add `Comment.depth = PositiveSmallIntegerField(default=0)` — denormalized at create time, capped at 3. Avoids recursive walks at render.
- Index on `(article, parent, created)` for the threaded ordering query.
- Migration is additive; existing rows get `parent=NULL`, `depth=0`.

## Key Technical Decisions
- **Adjacency list, not MPTT.** `django-mptt` is the textbook choice, but it adds a dependency, write-time tree maintenance, and complexity for a feature where we cap depth at 3. A self-FK + denormalized `depth` field is 30 lines and has no failure modes worth fearing.
- **Tombstone on delete, not cascade.** If a parent has children, soft-delete (set `content=""`, mark `is_deleted=True`) so the thread doesn't lose its spine. Standalone deletes (no children) still hard-delete.
- **One query, in-memory tree assembly.** `Comment.objects.filter(article=...).order_by("created").select_related("author")` once, then build the tree in Python. Avoids N+1 across depths.

## Risks & Open Questions
- **Depth-cap edge case.** When user replies to a depth-3 comment, server must reassign `parent` to the depth-3 comment itself (so the reply is also depth-3, sibling to the original). Test this explicitly.
- **Selectors contract.** Reply button is new — confirm it isn't already pinned in `realworld/specs/e2e/SELECTORS.md`. If e2e tests don't exist for it, that's fine; existing comment selectors must keep working.
- **Open question:** notification verb for replies — `commented` (existing) or new `replied`? Probably keep `commented` and let target_id point at the parent comment.

## Success Metrics
- Comment thread page renders in <100ms (p95) for 50-comment articles.
- 100% coverage on the new tree-build helper.
- E2e baseline stays green; new e2e covers the reply-and-render path.

## Rough Effort
M — model migration, view changes, template restructure, but the surfaces are all in `apps/comments` plus the article detail template.

## Dependencies
- None. Plays well with **20.01 Notifications** (reply triggers a "commented" notification on the parent comment's author).
