# PRD: Deployment Story

**Tier:** 4 &nbsp;·&nbsp; **Status:** Proposed &nbsp;·&nbsp; **Owner:** TBD

## Problem
There is a `Dockerfile` and a `docker-compose.yml` in the repo, but neither is production-ready: the Dockerfile is a single-stage build that ships `gcc` and dev sources to prod, the compose runs `runserver` (a dev server that loudly warns it shouldn't), and there is no deploy target — no staging, no prod, no CI/CD. The dev database is SQLite; production needs Postgres, and we have no migration story between the two. Until this PRD lands, the project can't be run anywhere except a developer's laptop, which means every other Tier 1–3 PRD is theoretical.

## Goals
- A multi-stage `Dockerfile` that builds a slim production image (no compiler, no test deps).
- A `docker-compose.yml` that boots web + Postgres + Redis locally with one command.
- A documented, repeatable deploy to one chosen target with HTTPS terminated and the app reachable on a public URL.
- 12-factor config: every prod-relevant setting reads from env vars (most already do).

## Non-Goals
- Multi-region / multi-AZ. One region is fine.
- Blue/green or canary deploys. Recreate-then-migrate is acceptable at our scale.
- Auto-scaling. One web pod + one worker pod is the starting point.
- Kubernetes. Out of scope; revisit only if we outgrow PaaS.

## User Stories
- As a developer, I run `docker compose up` and have web + db + redis running with hot-reload.
- As an operator, I push to `main` and CI builds + tags an image; a deploy command rolls it out.
- As an SRE, the prod container exits non-zero on misconfig (already true for `DATABASE_URL`).
- As a new contributor, the README has 5 lines that get me from `git clone` to a running local stack.

## UX Sketch
No application UI. Repository surface:
- `Dockerfile` rewritten as multi-stage (builder installs deps with `uv`, runtime stage copies `.venv` and source onto `python:3.12-slim`).
- `docker-compose.yml` extended with a `redis:7-alpine` service and a `worker` service (40.02) sharing the web image.
- `compose.prod.yml` overlay (or a separate target's deploy manifest) for production.
- New justfile recipes: `just docker-build`, `just docker-up`, `just docker-down`.
- README "Deployment" section with the chosen target's quickstart.

## Data Model Changes
None at the model level. **Migration from SQLite to Postgres:** `dumpdata --natural-foreign --natural-primary` on the SQLite db, restore via `loaddata` against a freshly-migrated Postgres. Document this as a one-shot script in `scripts/migrate_to_postgres.py`. (No prod data exists yet, so this is a forward-looking concern.)

## Key Technical Decisions
- **Deploy target: Fly.io.** Rationale: managed Postgres + Redis (Upstash add-on), Dockerfile-native (no buildpack lock-in), per-region pricing, and a credible free tier for staging. Alternatives considered: **Railway** (similar DX, slightly less mature on the Postgres side), **plain VPS + Caddy + systemd** (most control, most work — revisit if PaaS pricing becomes a problem). All three are swappable because the app is just a Docker image.
- **Production server: `gunicorn` with 2–4 workers**, behind the platform's TLS terminator. Alternative: `uvicorn` — only worth it if/when we go ASGI for Channels.
- **Static files: `whitenoise` middleware**, serving from `STATIC_ROOT` after `collectstatic`. Avoids needing S3/CDN at the start; revisit if traffic grows.
- **Secrets**: platform env vars (Fly secrets), never committed. `SECRET_KEY` must come from env in prod (settings.py already supports this).
- **CI/CD**: GitHub Actions builds image on `main`, tags with commit SHA, deploys via `flyctl deploy --image`. Hooks into `just check-all` first — same gates as local.

## Risks & Open Questions
- **The current `DEBUG=True make run-debug` shortcut.** Once prod exists, contributors must not accidentally point at prod. Mitigation: separate `.env.example` for local vs. a documented secret-store path for prod.
- **Migration of `db.sqlite3` checked into the repo.** Add `db.sqlite3` to `.gitignore` and stop tracking it before this PRD lands; otherwise prod operators will inherit dev fixtures.
- **Open question:** do we run worker (40.02) as a sibling Fly process or a separate machine? Recommendation: sibling process group, one image.

## Success Metrics
- `docker compose up` from a fresh clone reaches a working local stack in <90s.
- Image size <250MB (multi-stage trims build deps).
- A green CI build deploys to staging without manual steps.

## Rough Effort
L — Dockerfile rewrite, compose extension, CI pipeline, target setup, secret wiring, and migration script. Mostly ops glue; little app code.

## Dependencies
- **Unblocks:** practically everything operational. **40.02 Background Jobs** needs Redis from compose, **40.03 Caching** needs Redis from compose, **10.01 Password Reset** needs `DEFAULT_FROM_EMAIL` configured in a real env, and any Tier 2/3 PRD that touches Postgres-only features (full-text search 10.02, JSON fields) needs Postgres in prod.
- **Blocked by:** none. Land this and 40.01 in parallel.
