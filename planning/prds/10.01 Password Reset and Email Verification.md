# PRD: Password Reset and Email Verification

**Tier:** 1 &nbsp;·&nbsp; **Status:** Proposed &nbsp;·&nbsp; **Owner:** TBD

## Problem
Today `apps/accounts/register_view` creates a fully-active user the moment the form validates — no email confirmation, no proof the address is real. There is no "forgot password" flow at all, so a user who forgets their credentials is effectively locked out. Both gaps are table-stakes for any blogging app that takes itself seriously and a precondition for sending any other transactional mail (notifications, exports).

## Goals
- New signups must verify their email before they can publish or comment.
- Existing users can request a password reset link and set a new password from the link target.
- All transactional email goes through a real provider with bounce visibility, not Django's console backend.

## Non-Goals
- Social login / OAuth.
- Magic-link login (passwordless). Verification links are single-purpose.
- Re-verification when an existing user changes their email in `/settings` (Tier 2 follow-up).

## User Stories
- As a new visitor, I can sign up and receive a verification email so that I can prove I own the address.
- As a verified user, I can request a password reset and follow a link to choose a new password.
- As a user with an unverified account, I see a banner prompting me to resend the verification email.
- As an operator, I can see delivery + bounce events for verification and reset mail.

## UX Sketch
Signup flow gains an interstitial "check your email" page after `register_view` succeeds. The user record is created with `is_active=False` (or a separate `email_verified` flag — see below). A new `verify_email_view` consumes Django's signed token, flips the flag, and logs the user in. Login attempts against an unverified account land on a "resend verification" page.

Forgot-password is a `Sign in` page link to `/password-reset/`, then the standard four-view Django flow (`PasswordResetView` → done → confirm → complete), reskinned with the existing base template. No HTMX — these are throwaway one-shot pages.

## Data Model Changes
- `User.email_verified: BooleanField(default=False)` — additive, nullable-safe; preferred over flipping `is_active` so admins keep the existing meaning of "active". Backfill `True` for existing users in the data migration.

## Key Technical Decisions
- Use Django's built-in `PasswordResetView` / `PasswordResetConfirmView` and `default_token_generator` rather than a third-party package — battle-tested, fits stack, no new deps for the reset half.
- Email backend: **Anymail with Postmark** (alternative considered: Amazon SES). Postmark wins on developer ergonomics and deliverability for transactional-only volume; SES is cheaper at scale but more setup. Both are swappable behind Anymail.
- Templates live in `templates/registration/` (Django's default lookup path).
- Gate publish/comment on `request.user.email_verified` via a small decorator in `helpers/`.

## Risks & Open Questions
- **Risk:** Verification token URLs leak via referer headers. Mitigation: invalidate token on use (Django's default), short TTL (24h).
- **Open question:** Do unverified users see a read-only site or a hard wall at login? Recommendation: read-only — they can browse, just can't write.

## Success Metrics
- >80% of new signups verify within 24h.
- 0 e2e regressions; new e2e covering verify + reset happy paths.
- Bounce rate < 2% (Postmark dashboard).

## Rough Effort
M — three new flows, one migration, one new dependency (Anymail), and a new gating decorator that touches `article_create_view`, `article_edit_view`, and `comment_create_view`.

## Dependencies
- None for the feature itself. Provider account (Postmark) and `DEFAULT_FROM_EMAIL` config are operational prerequisites.
