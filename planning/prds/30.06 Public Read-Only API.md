# PRD: Public Read-Only API

**Tier:** 3 &nbsp;·&nbsp; **Status:** Proposed &nbsp;·&nbsp; **Owner:** TBD

## Problem
This implementation's defining thesis is *no API, no SPA* — server-rendered HTML over HTMX, all the way down. That thesis still holds for the human-facing product, but it has costs the original architecture didn't anticipate. There's no way for a third party to embed an article list in another site, no way for a static-site generator to mirror an author's output, no way to compare us against the rest of the RealWorld implementations on their own terms (the spec defines a JSON API contract that every other implementation honors). A read-only public API answers all three without compromising the HTMX-first interactive UX.

## Goals
- A versioned public API at `/api/v1/` exposes read-only endpoints for articles, profiles, and tags.
- Endpoint shapes match the RealWorld spec contract closely enough that the standard RealWorld API test suite passes for the read paths.
- The API has its own OpenAPI schema, autogenerated, served at `/api/v1/openapi.json` with Swagger UI at `/api/v1/docs`.
- The API is rate-limited per-IP, returns clean JSON errors, and is fully covered by tests separate from the HTMX path.

## Non-Goals
- Write endpoints (POST/PUT/DELETE for articles, comments, favorites, follows). Explicitly out of scope for v1 — those flows belong to the HTMX UI; revisit only if a real partner integration needs them.
- API auth tokens / API keys. v1 is anonymous and read-only; rate limit is the only protection. (`/api/v1/articles/feed` — the personalized "Following" feed — is therefore omitted; it requires auth.)
- GraphQL.
- Webhooks.

## User Stories
- As a third-party developer, I can `GET /api/v1/articles?limit=20&tag=django` and receive a JSON list of articles matching the RealWorld spec shape.
- As a third-party developer, I can `GET /api/v1/profiles/<username>` and get a profile JSON document.
- As a third-party developer, I can `GET /api/v1/tags` and receive the list of tags.
- As a third-party developer, I can open `/api/v1/docs` in a browser and try every endpoint live.
- As an operator, I can see API traffic separated from HTML traffic in logs (different URL prefix, different rate-limit bucket).

## UX Sketch
No human UI for v1 except `/api/v1/docs` — Swagger UI rendered from the autogenerated OpenAPI schema. New Django app `apps/api/` with one `routers/v1.py` exposing the endpoint set. No templates, no HTMX — pure JSON.

## Data Model Changes
None. The API is a read-only projection of the existing `Article`, `User`, and `taggit.Tag` models.

## Key Technical Decisions
- **`django-ninja`** for the API layer. Reasons: type-hint-driven schemas (Pydantic), autogenerated OpenAPI, fast (Django-native, no DRF metaclass overhead), feels like FastAPI but without leaving Django. Alternative considered was **Django REST Framework** — the stalwart, but its serializer machinery is a heavier ergonomic tax for a read-only API and OpenAPI generation requires extra wiring.
- **Architectural-decision posture: this revisits the "no API" thesis intentionally and narrowly.** The thesis was always about the *human-facing UI* not being an SPA-against-an-API. It was never about refusing all programmatic access. The API lives at a separate URL prefix, has its own app, its own tests, and is read-only — it cannot grow into "the real backend" by accident because writes still go through HTML form posts handled by `articles/views.py`. If we ever build a write API, it should be a separate, deliberate PRD with its own auth design.
- **Endpoint shape mirrors RealWorld spec** for `articles`, `articles/{slug}`, `articles/{slug}/comments`, `profiles/{username}`, `tags`. Standard RealWorld contract tests run against us as a smoke test — gives us a free conformance check.
- **`django-cors-headers`** with a permissive `CORS_ALLOWED_ORIGINS = ["*"]` for `GET` only. Public read API = anyone can fetch.
- **Rate limit: 60 requests / minute / IP** via `django-ratelimit` (already a dep if 30.04 lands first). 429 responses with `Retry-After`.
- **Caching:** `Cache-Control: public, max-age=60` on list endpoints; cache the rendered JSON per query-string in Django's cache framework.

## Risks & Open Questions
- **Risk:** API drifts from HTMX UI as the model evolves — bug fixed in one path, reproduced in the other. Mitigation: the API queries call into the same `ArticleQuerySet.with_favorites()` helper the views use; serialization is the only API-specific layer.
- **Risk:** Once an API exists, the pressure to add write endpoints becomes constant. Mitigation: accept it now, defer it explicitly per the PRD, and require a new PRD to revisit.
- **Open question:** Honor `is_favorite` for anonymous API callers? It's always `false` for them; document and move on.
- **Open question:** Should the OpenAPI schema be checked into the repo for diffability in PRs? Recommend yes — small file, big win for review.

## Success Metrics
- RealWorld read-path conformance test suite passes against `/api/v1/`.
- API response p95 latency < 100ms (cached) / < 250ms (uncached).
- 0 regressions in the HTMX-driven e2e suite — the API is fully separate.
- 100% unit-test coverage on the new `apps/api/` module (matches the project gate).

## Rough Effort
M — new app, ~8 endpoints, schema definitions, OpenAPI / Swagger wiring, rate-limit + CORS config, separate test module. No migration. New dependency (`django-ninja`).

## Dependencies
- **30.04 Moderation** (Tier 3, this batch) — soft-deleted articles must not appear in API responses. The shared default manager filter handles this automatically as long as the API uses `Article.objects` (not `all_objects`), which it should.
- **10.05 Markdown Rendering Hardening** (Tier 1) — API article responses include both raw `body` and rendered `bodyHtml`; the rendered side reuses the sanitized pipeline.
