# PRD: Background Jobs

**Tier:** 4 &nbsp;·&nbsp; **Status:** Proposed &nbsp;·&nbsp; **Owner:** TBD

## Problem
Today every request runs to completion in the WSGI worker — there is no async path. That works fine for the current feature set, but several planned features either can't ship or will block the request thread without it: transactional email (10.01), notification fan-out for popular authors (20.01), search index updates (10.02), and image thumbnail generation (10.04). Sending an SMTP message inline is a 1-second hit on every signup; fanning out 1k notifications inline turns a favorite click into a 30-second timeout. We need a worker tier before any of those PRDs are buildable.

## Goals
- A `enqueue(func, *args)` API that any view or signal handler can call without thinking.
- Workers run in a separate process (containerized for prod) and survive crashes via a durable broker.
- Failed jobs are retried with backoff and ultimately surface in Sentry.

## Non-Goals
- Cron-style periodic tasks. We have no real use case yet — revisit when one shows up.
- Distributed task graphs / chords / canvas. We're fan-out + retry, nothing fancier.
- ASGI / Channels. Different problem (websockets), different solution.

## User Stories
- As a developer, I can write `enqueue(send_verification_email, user.id)` and forget about it.
- As an operator, I run one extra container (`worker`) alongside web and see jobs flow.
- As an SRE, when Redis is down, jobs queue locally and replay on reconnect — or the view fails fast and Sentry yells. (We pick: fail fast.)
- As a developer, my unit tests run jobs synchronously by default so I don't need a Redis in CI.

## UX Sketch
No user-facing UI. Internally: a `helpers/jobs.py` module wraps the chosen library so view code calls `from helpers.jobs import enqueue`. Tests set a `JOBS_EAGER=True` env var that runs jobs inline. A new `just worker` justfile recipe boots the worker process for local dev. Production runs `python manage.py qcluster` (or equivalent) as a sibling container.

## Data Model Changes
- Library-managed tables only (django-q2 creates `django_q_*` tables via its own migrations). No app-level model changes.

## Key Technical Decisions
- **Pick `django-q2`.** Rationale: Django-native (uses Django ORM for the result store, Django settings for config, Django admin for the queue), maintained fork of django-q, and the operational footprint is one extra process — no Celery beat, no result backend to choose. Redis serves as the broker only.
- **Alternatives considered:**
  - **Celery** — industry standard but heavyweight: separate config file, beat scheduler, and a result backend decision. Overkill for our load.
  - **RQ** — simpler than Celery but less Django integration; we'd hand-roll the admin and management commands django-q2 gives us free.
  - **Dramatiq** — modern API, good ergonomics, but smaller community; less material when something breaks at 2am.
- **Broker:** Redis (shared with the cache from 40.03 — one Redis instance, two logical DBs).
- **Test mode:** `Q_CLUSTER = {"sync": True}` when `JOBS_EAGER=True`, so unit tests stay fast and don't need a broker.
- **Observability:** workers inherit the JSON logging + Sentry config from 40.01; ensure the request-ID contextvar is replaced by a `job-id` contextvar inside worker tasks.

## Risks & Open Questions
- **At-least-once delivery.** Jobs must be idempotent. Document this in `helpers/jobs.py` and code-review for it.
- **Local dev friction.** Devs without Redis running can't test job flows end-to-end — `JOBS_EAGER` covers unit tests but not Playwright. Add a `just worker` and a docker-compose Redis from 40.04.
- **Open question:** do we run one worker pool or split queues by priority (`default`, `email`, `index`)? Start with one; split when one slow job type starves the others.

## Success Metrics
- p95 view latency for `register_view` drops to <100ms once email sends move to a job.
- 0 jobs lost across a worker restart (durable broker).
- Worker container has a Sentry "release" tag matching web.

## Rough Effort
M — one new dep, one Redis service in compose, one `helpers/jobs.py` shim, one `just` recipe, and a config branch in settings. The cost is mostly operational (now there are two processes to run) not code.

## Dependencies
- **Blocked by:** **40.01 Observability** (workers need the same logging + Sentry config) and **40.04 Deployment Story** (Redis service must exist in compose / prod).
- **Unblocks:** **10.01 Password Reset / Email** (move email send off the request path), **20.01 Notifications** (fan-out), **10.02 Search** (async index updates), **10.04 Image Thumbnails** (generation).
