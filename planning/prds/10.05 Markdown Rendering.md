# PRD: Markdown Rendering

**Tier:** 1 &nbsp;·&nbsp; **Status:** Proposed &nbsp;·&nbsp; **Owner:** TBD

## Problem
Article body and comments are rendered as plain text — newlines, no formatting, no links, no code blocks. (There is a `markdown_filter` template tag in `apps/articles/templatetags/` that calls `markdown` + `nh3`, but per the per-app docs it's wired only at the article-detail surface and not exercised end-to-end with editor/preview affordances.) For a developer-audience blogging app this is the difference between "useful" and "toy". Authors paste code, links, and images expecting formatting; today they get a wall of text.

## Goals
- Article bodies render Markdown, including fenced code blocks with syntax highlighting.
- Comment bodies render Markdown (a constrained subset).
- Editor has a live "Preview" tab so authors see what readers will see.
- All rendered HTML is sanitized; no XSS via crafted input.

## Non-Goals
- WYSIWYG editing — the editor stays textarea-based.
- Real-time collaborative editing.
- Custom Markdown extensions (mentions, embeds) — Tier 2.
- Migration of existing plain-text content — it's already valid Markdown (paragraphs work).

## User Stories
- As an author, I can use `**bold**`, headings, lists, links, and fenced code blocks in my article body.
- As an author in the editor, I can click a "Preview" tab to see the rendered version, then "Edit" to go back.
- As a commenter, I can use a constrained Markdown subset (no headings, no images) so comments don't blow up the page.
- As a reader, code blocks have syntax highlighting matching the language hint.
- As an attacker, my crafted `<script>` payload in a comment is sanitized to nothing.

## UX Sketch
Article editor (`apps/articles/forms.py::ArticleForm`) gets a tab strip above the body textarea: **Edit** | **Preview**. "Preview" is HTMX: `hx-post` to a new `article_preview_view` that takes the current body, renders it, returns sanitized HTML into a target div. No DB write — the view is stateless. Same pattern reused for comments below the article.

Reader-facing rendering happens in templates via the existing `render_markdown` template tag — broaden its use to article bodies wherever they appear (detail page, draft preview from PRD 10.03), plus the comment list.

Comment Markdown uses a restricted bleach allowlist (inline only — `em`, `strong`, `code`, `a`, plus paragraphs). Article Markdown allows the full block set: headings (h2+, never h1), lists, blockquotes, fenced code, tables, images.

## Data Model Changes
- None. Content is already stored as text; rendering happens at display time. (Storing pre-rendered HTML was considered and rejected — render-on-read is fast enough for our scale and avoids a backfill.)

## Key Technical Decisions
- **`markdown` (Python-Markdown) + `bleach`** for parse + sanitize. Alternative considered: `markdown-it-py` (faster, CommonMark-strict). Sticking with Python-Markdown because the project already imports `markdown` in the existing template tag — one less dep to introduce. Sanitization stays on `bleach` (or `nh3`, already imported in the existing template tag — pick one and standardize).
- **Pygments** for code highlighting via the `fenced_code` + `codehilite` Markdown extensions. CSS lives in `static/`.
- Keep two sanitizer profiles: `ARTICLE_ALLOWLIST` and `COMMENT_ALLOWLIST` — comment profile is a strict subset.
- Render-on-read, not render-on-write. Cache rendered HTML per-article in Django's cache for 5 minutes (same TTL as the tags cache in `apps/articles/constants.py`) — invalidate on edit. Comments don't get cached; they're cheap.

## Risks & Open Questions
- **Risk:** XSS via novel sanitizer bypass. Mitigation: pin sanitizer version, run untrusted input through tests, add a regression test for every disclosed bypass.
- **Risk:** Pygments adds page weight. Mitigation: lazy-load CSS only on pages that contain `<pre class="codehilite">`.
- **Open question:** Standardize on `bleach` or `nh3`? `nh3` is already used in the existing template tag and is a Rust-backed `ammonia` binding — faster, actively maintained. Recommendation: `nh3`.

## Success Metrics
- 0 e2e regressions; new e2e covering author-writes-markdown → reader-sees-rendered.
- 0 XSS findings from a manual fuzzing pass + the crafted-payload test suite.
- Preview-tab usage tracked client-side; aim for >40% of editor sessions using preview.

## Rough Effort
M — one new view (preview), template-tag wiring across article/comment surfaces, two sanitizer profiles, Pygments CSS, editor tab UI, unit + e2e coverage.

## Dependencies
- None. **Should land before 10.03 Drafts** so draft preview pages show the rendered Markdown authors will publish.
