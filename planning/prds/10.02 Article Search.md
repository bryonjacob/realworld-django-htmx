# PRD: Article Search

**Tier:** 1 &nbsp;·&nbsp; **Status:** Proposed &nbsp;·&nbsp; **Owner:** TBD

## Problem
Readers can filter the global feed by tag (the popular-tags sidebar in `apps/articles/views.py::_build_feed`), but there is no way to find an article by title or content. Once the corpus grows past two pages, discovery breaks down — the only fallback is scrolling pagination. Authors writing about the same topic across multiple posts have no way for readers to navigate that body of work.

## Goals
- Users can type a query in a header search bar and get a ranked list of matching articles.
- Search covers `title`, `summary`, and `content` — tag filtering stays as it is.
- Latency p95 < 200ms on a 10k-article corpus on Postgres.

## Non-Goals
- Search across users, comments, or tags (Tier 2).
- Faceted search / filters beyond the existing tag chip behaviour.
- Typo tolerance / fuzzy matching.
- Saved searches, search history.

## User Stories
- As a reader, I can type "django htmx" in the header search bar and see articles whose title or body matches.
- As a reader, I see results ranked by relevance, not just recency.
- As a reader on the search page, I can paginate through results using the same UX as the home feed.
- As a developer running locally on SQLite, search still works (degraded but functional).

## UX Sketch
Add a search input to `templates/_layouts/_header.html` (visible to anonymous + authenticated users). Submitting hits a new `search_view` at `/search/?q=…`. Results render in the same article-preview template the home feed uses — no separate "search result" component. Empty query redirects home; zero results renders an empty-state partial.

HTMX optional but desirable: the input gets `hx-get="/search/" hx-trigger="keyup changed delay:300ms"` targeting the feed container, so typing live-updates results without a full page load. Falls back gracefully without HTMX.

The search route reuses `_feed_queryset`-style composition — extend it with a `search` feed type that takes a query string, returns the filtered queryset + tab name, then flows through the existing pagination/partial machinery.

## Data Model Changes
- `Article` gains a `SearchVectorField` (Postgres only) plus a `GinIndex` on it. Maintained via a `pg_trgm` trigger or a `post_save` signal that calls `SearchVector("title", "summary", "content")`.
- On SQLite (dev/test), the field is unused — the queryset falls back to chained `Q(title__icontains=q) | Q(summary__icontains=q) | Q(content__icontains=q)`.

## Key Technical Decisions
- Use **Django's `django.contrib.postgres.search`** (`SearchVector`, `SearchQuery`, `SearchRank`) rather than a separate engine. Alternative considered: Meilisearch / Typesense — more powerful but a full new service to operate. Postgres FTS is plenty for a blogging app's corpus size.
- Engine selection lives in the queryset, not the view: `Article.objects.search(q)` introspects `connection.vendor` and picks FTS vs LIKE. Keeps `_feed_queryset` ignorant of the backend.
- Title gets an `A` weight, summary `B`, content `C` so headlines rank higher.

## Risks & Open Questions
- **Risk:** SearchVector update on every save adds write cost. Mitigation: trigger-based update is async to the Django save path; signal-based is simple and acceptable for our write volume.
- **Open question:** Stem in English only, or skip the language config? Default to `'english'` and revisit if i18n lands.

## Success Metrics
- p95 search latency < 200ms (Postgres, 10k articles).
- Search bar usage tracked via simple event log; aim for >15% of sessions issuing at least one query within a month of launch.

## Rough Effort
M — one new view, one queryset method, one migration with a Postgres-conditional index, one header partial change, plus e2e coverage.

## Dependencies
- None. Works on the current SQLite dev setup; Postgres path lights up when the prod DB switches.
