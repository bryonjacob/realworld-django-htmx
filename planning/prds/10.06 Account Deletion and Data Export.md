# PRD: Account Deletion and Data Export

**Tier:** 1 &nbsp;·&nbsp; **Status:** Proposed &nbsp;·&nbsp; **Owner:** TBD

## Problem
There is no way for a user to delete their account or get a copy of their data. `/settings` (`apps/accounts/views.py::settings_view`) lets users edit profile fields and that's it. This is GDPR Article 17 (right to erasure) and Article 20 (right to portability) territory — both required to operate in the EU and table-stakes for trust regardless of jurisdiction. Today the only way to leave is to email a human and hope they have admin shell access.

## Goals
- Authenticated users can delete their account self-serve, with a confirmation step.
- Authenticated users can download a JSON export of their profile, articles, and comments.
- Deletion behaviour is well-defined and consistent — no orphaned data, no orphaned references.
- Both flows are auditable in admin (action log of deletions, no log of export contents).

## Non-Goals
- Soft delete / undo / 30-day grace period (Tier 2 if we want it later).
- Export of who-followed-me / who-I-followed graph as a separate file (it's included in the JSON, not a separate CSV).
- Data import from another instance.
- Export of data the user doesn't own (other people's comments on their articles, etc. — not theirs to take).

## User Stories
- As a user, I can click "Download my data" in `/settings` and get a JSON file with everything I've created.
- As a user, I can click "Delete account", type my email to confirm, and the account is gone immediately on submit.
- As a user, after deletion, my email address is freed for re-signup (no soft-lock on the email).
- As a reader, articles and comments authored by deleted users either vanish or display "[deleted]" — chosen consistently.
- As an operator, I can see a count of deletions per month in admin without seeing the deleted users' details.

## UX Sketch
`/settings` page (`apps/accounts/templates/...`) gains a **"Danger zone"** section at the bottom with two buttons:

1. **"Download my data (JSON)"** — hits a new `data_export_view`, returns `application/json` with `Content-Disposition: attachment`. Sync — payloads are small for a blogging app's per-user volume.
2. **"Delete my account"** — opens a confirmation page (full page, not a modal) requiring the user to type their email address to enable the submit button. Submitting hits `account_delete_view`, runs the deletion in a transaction, logs the user out, redirects home with a flash message.

No HTMX needed — these are one-shot destructive actions where a full-page step is the right tone.

## Data Model Changes
- None to schema. Deletion semantics rely on existing FK behaviour:
  - `Article.author` is `on_delete=CASCADE` today — articles vanish with the user.
  - `Comment.author` is `on_delete=CASCADE` — same.
  - **Decision needed (see Risks):** the cascading is a strong default but loses comment threads on others' articles. Consider switching `Comment.author` to `SET_NULL` and a nullable FK so threads stay readable as `[deleted]`. That's a migration.

## Key Technical Decisions
- **JSON for export**, not CSV or a zip of mixed formats. JSON round-trips structure (lists of tags, references between articles and comments) without flattening loss. Alternative considered: zip of per-table CSVs — uglier, no clear win.
- Use Django's `DjangoJSONEncoder` plus a thin per-model `to_export_dict()` method on `User`, `Article`, `Comment`. Keeps export logic next to the model definition.
- **Confirmation by retyping email**, not by password. Catches the "wrong tab / wrong account" mistake without a second auth challenge that a recently-logged-in user wouldn't expect.
- Deletion runs in `transaction.atomic()` — partial deletes are worse than no delete.

## Risks & Open Questions
- **Risk:** Cascading deletes wipe comment threads on other authors' articles. Open question: CASCADE (current behaviour, simpler) or SET_NULL with a placeholder display name (preserves discussion context, but adds nullable FK + display-name handling everywhere comment author is shown). Recommendation: **SET_NULL for `Comment.author`**, keep CASCADE for `Article.author` (articles are the user's voice; comments are part of someone else's discussion).
- **Risk:** Export endpoint is a slow query for prolific users. Mitigation: it's per-user; even a 10k-article author finishes in under a second. Add a rate limit (1 export per minute) to prevent abuse.
- **Open question:** Do we email a "your account was deleted" receipt? Recommendation: yes, once 10.01 is in.

## Success Metrics
- Self-serve deletion path tested by e2e; 0 admin-shell deletions needed.
- Export response time p95 < 1s for the seeded user fixture.
- 0 orphaned-FK exceptions in error logs post-launch.

## Rough Effort
M — two new views, one confirmation page, optional FK migration on comments, per-model export serialization, "Danger zone" template work, unit + e2e coverage. Migration is the main risk lever — without it this is an S.

## Dependencies
- **10.01 Password Reset and Email Verification** is a soft prerequisite for the deletion-receipt email but not for the core flow.
