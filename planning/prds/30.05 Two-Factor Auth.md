# PRD: Two-Factor Auth

**Tier:** 3 &nbsp;·&nbsp; **Status:** Proposed &nbsp;·&nbsp; **Owner:** TBD

## Problem
Auth today is email + password and nothing else. A reused password from a breached site is enough to take over any account, including staff. For a public-facing site that hosts user-generated content and has a Django admin, that's a meaningful gap; for staff in particular, it's a real liability — a single compromised admin account could soft-delete or hard-edit any article. We need an opt-in second factor for users and a forced second factor for staff.

## Goals
- Logged-in users can enable TOTP-based 2FA from `/settings`, scanning a QR code with any authenticator app (Google Authenticator, 1Password, Authy, Bitwarden).
- Users with 2FA enabled are prompted for a 6-digit code after password entry on every login.
- Users get one-time backup codes at enrollment to recover if they lose their device.
- All staff (`is_staff=True`) accounts must have 2FA enabled to access `/admin/`; the admin login enforces this.

## Non-Goals
- SMS-based 2FA (deliberately excluded — SIM-swap risk, and the carrier integration cost isn't worth it for a v1 that already supports TOTP).
- Hardware-key only / WebAuthn-only flows. Discussed below.
- Per-action step-up (re-prompt for 2FA before destructive actions). Future polish.
- Recovery via email link bypassing 2FA — that defeats the point.

## User Stories
- As a security-conscious user, I can enable 2FA in my settings and scan a QR code to enroll.
- As a user with 2FA enrolled, I am prompted for a code after I enter my password on login.
- As a user who lost my phone, I can use one of my saved backup codes to log in and re-enroll a new device.
- As a staff member, I cannot reach `/admin/` until I've enrolled in 2FA.
- As an attacker with a stolen password, I cannot log in without also having the user's authenticator.

## UX Sketch
**Settings page** gains a "Two-factor authentication" section: status (`Disabled` / `Enabled since 2026-04-01`), `[Enable]` button. Enabling opens an HTMX-loaded panel with a QR code (`pyotp` URI rendered server-side via `qrcode`), a confirmation code input, and the list of backup codes (shown once, with a "Save these somewhere safe" warning).

**Login flow** becomes two-step for 2FA-enabled accounts: `login_view` validates credentials, sets a short-lived signed `pre_2fa` token in the session, and redirects to `verify_2fa_view` which prompts for the code. The code form has a "Use a backup code instead" link.

**Admin guard** is a tiny middleware: if `request.path` starts with `/admin/` and `request.user.is_staff and not user.has_2fa`, redirect to `/settings/?enroll_2fa_required=1` with a flash message.

## Data Model Changes
- All handled by `django-otp`'s `TOTPDevice` and `StaticDevice` (backup codes) — existing third-party tables, additive migration.
- `User.has_2fa: BooleanProperty` — computed property that checks for any confirmed `TOTPDevice`. No column needed.

## Key Technical Decisions
- **`django-otp` + `django-otp-totp`** for the TOTP machinery. It's the de facto standard, plays nicely with Django's auth, and `StaticDevice` gives us backup codes for free. Alternative considered: `django-two-factor-auth` — a higher-level wrapper around `django-otp` that includes pre-built views and templates. Rejected because its templates fight our HTMX-driven settings page and our reskin would be more work than wiring `django-otp` directly.
- **WebAuthn / passkeys explicitly considered and deferred.** Passkey UX is genuinely better for end users, the libraries (`django-passkeys`, `webauthn`) are workable, and platform support (iCloud Keychain, 1Password, Chrome) is now broad enough that it's not a fringe technology. We defer because: (a) passkeys-only excludes users without a sync-enabled platform, so we'd need TOTP anyway as a fallback; (b) RealWorld's reference implementations all assume password+TOTP, and diverging adds e2e complexity; (c) starting with the more conservative pattern lets us layer passkeys in later as a *third* option from settings without re-architecting auth.
- **Forced 2FA for staff via middleware,** not via a custom admin override — middleware is one place to read, applies to any future staff-only URL prefix.
- **Backup codes:** 10 codes, 8 chars, single-use, regenerable (regenerating invalidates the old set).

## Risks & Open Questions
- **Risk:** Users lose phone *and* backup codes. Mitigation: documented support flow — verify identity out-of-band, staff resets via Django admin (which itself is 2FA-gated). Not automatable; that's the point.
- **Risk:** 2FA breaks the e2e suite (login flow changes). Mitigation: e2e users start without 2FA; a small dedicated suite covers the 2FA flow only.
- **Open question:** Trust-this-device cookie (skip 2FA for 30 days)? Convenient, but lowers the bar. Recommend not for v1.

## Success Metrics
- 100% of staff accounts enrolled in 2FA within one week of launch (operational gate).
- >5% of regular-user accounts opt into 2FA in the first 90 days (rough demand signal).
- 0 e2e regressions; new e2e suite covers enroll + login + backup code paths.

## Rough Effort
M — two new dependencies, two new view flows (enroll, verify), one middleware, settings-page additions, e2e coverage. Small migration footprint (mostly handled by `django-otp`).

## Dependencies
- **10.01 Password Reset and Email Verification** (Tier 1) — 2FA on top of an unverified email creates a worse lockout if the user loses the device, since you can't even reset the password reliably. Should land verification first.
