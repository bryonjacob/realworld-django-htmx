# PRD: Image Uploads

**Tier:** 1 &nbsp;·&nbsp; **Status:** Proposed &nbsp;·&nbsp; **Owner:** TBD

## Problem
`User.image` is a `URLField` — the user has to host their avatar somewhere else and paste a link. Articles have no cover image at all, so the home-feed list is a wall of text. Both choices push hosting onto users we should be hosting for, and there is no way to validate or normalise what gets posted (broken links, hotlinking, mixed content, NSFW URLs are all possible today).

## Goals
- Users can upload an avatar from `/settings` instead of pasting a URL.
- Authors can attach an optional cover image to an article in the editor.
- All uploads land in object storage (S3-compatible), served via signed or public URLs.
- Generated thumbnails for list views; original retained for detail pages.

## Non-Goals
- Inline images inside article body (deferred until 10.05 Markdown ships — markdown image syntax can reuse the same upload endpoint later).
- Image editing (crop, rotate) in the browser.
- Galleries / multiple images per article.
- Video / GIF uploads.

## User Stories
- As a user in `/settings`, I can choose a file from my device and see my new avatar after save.
- As an author in the editor, I can drag-and-drop or browse to a cover image; the article preview shows it.
- As a reader on the home feed, I see article cover thumbnails in the article-preview component.
- As an operator, uploaded files live in S3, not on the web server's local disk.

## UX Sketch
`/settings` form (`apps/accounts/forms.py::SettingsForm`) gains a file input alongside the existing image URL field. Both supported during transition: if a file is uploaded, it wins; otherwise URL field used. After 10.04 ships and bakes, URL field can be removed (Tier 2 cleanup).

Article editor (`apps/articles/forms.py::ArticleForm`) gains a `cover_image` file field above the title. Article detail page renders the cover hero-style above the title; article-preview list cards get a left-side thumbnail.

Server pipeline: on save, Pillow generates a 320x180 thumbnail and a 1200x630 social-card-sized version; both stored alongside the original. Templates pick the appropriate size.

## Data Model Changes
- `User.avatar: ImageField(upload_to="avatars/", null=True, blank=True)` — coexists with the legacy `image: URLField` until migration completes.
- `Article.cover_image: ImageField(upload_to="covers/", null=True, blank=True)`.
- `Article.cover_thumbnail: ImageField(upload_to="covers/thumbs/", null=True, blank=True)` — populated by post-save handler.

## Key Technical Decisions
- **django-storages with S3 backend** (alternative considered: Cloudinary). django-storages is the Django-native choice; works against AWS S3, Cloudflare R2, MinIO, DigitalOcean Spaces — i.e. anywhere we end up. Cloudinary bundles transformation but is a heavier dep with vendor lock-in.
- **Pillow** for thumbnail generation in a `post_save` signal handler. Synchronous is fine at our write volume; revisit with Celery if it ever blocks request latency.
- Local dev uses Django's `FileSystemStorage` via env-var `STORAGE_BACKEND` switch in `config/settings.py` (mirrors the existing `DEBUG`-controlled DB selection pattern).
- File-size cap (5MB) and MIME-type allowlist (jpg/png/webp) enforced in form `clean()` — never trust the client.

## Risks & Open Questions
- **Risk:** Storage costs from unbounded uploads. Mitigation: per-user quota (count of objects, simple to add later) + size cap up front.
- **Risk:** EXIF metadata leaks user location. Mitigation: strip EXIF in the thumbnailer.
- **Open question:** Public-read bucket vs signed URLs? Recommendation: public for avatars + covers (this is a public blog), signed only if we add private content later.

## Success Metrics
- >50% of newly-edited profiles use the upload field within a month.
- 0 web-server disk usage growth from media (proves storage backend is doing its job).
- p95 upload-to-thumbnail latency < 2s.

## Rough Effort
L — two model fields with a post-save thumbnailer, two form changes, settings-backend wiring, env-var-aware storage selection, new dependency (django-storages + Pillow + boto3), media-URL changes across templates.

## Dependencies
- None. Operational prerequisite: an S3-compatible bucket and credentials in env.
